# Audit or adopt an existing system

**Use when:** assessing UI/system consistency, reconciling undocumented assets, or adopting a baseline. Defining behavior: observation does not approve or mutate the system.

**Inputs:** relevant live UI, canonical assets, documentation, decision records, task boundaries and tool capabilities.

1. DISCOVER relevant artifacts read-only and identify canonical sources versus instances, detached copies, experiments and deprecated assets.
2. CONTRACT using [system-model](../protocol/system-model.md): classify approved definitions, verified conventions, inferred patterns, conflicts and missing requirements. Preserve identifiable authority; request focused confirmation only where dependent work needs it.
3. PLAN an inspection against the task's scope. Use [layout-evidence](../protocol/layout-evidence.md) for verification audits; do not require numeric exports for research-only inventories.
4. Gather actual evidence and report drift separately from uncertain conventions. Map to a neutral registry only when useful; conversion does not replace the canonical library or approve inferred values.
5. PRESENT findings, evidence, severity, limitations and the smallest decisions needed. Repairs require the [refine-screen](refine-screen.md) route; definition changes require [design-system change](design-system-change.md).

**Complete when:** findings are traceable to sources and authority/limitations are explicit, without unrequested mutations.

**Recovery:** conflicting sources block dependent decisions, not safe inspection. Unavailable evidence becomes UNVERIFIABLE; missing history is never filled with invented approval records.
