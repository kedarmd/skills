# Canonical change or migration

**Use when:** adding, changing, removing, deprecating or migrating canonical tokens, components, variants, states or composition rules. Defining behavior: approved proposal revision precedes dependent mutations.

**Inputs:** authoritative baseline, product need, reuse search, affected consumers, compatibility requirements and decision evidence.

1. DISCOVER canonical sources and usage. CONTRACT with [system-model](../protocol/system-model.md) and [change-control](../protocol/change-control.md), which owns proposal contents and approval rules.
2. Present the exact scoped proposal and isolated noncanonical preview. Include migration, compatibility, rollback and behavior preservation for affected consumers. Existing approval covers only its identifiable scope/revision.
3. Await explicit approval before canonical writes or dependent implementation. Independent authorized work may continue. Rejection returns to proposal revision, not implementation.
4. PLAN geometry changes with [layout-construction](../protocol/layout-construction.md). EXECUTE precisely the accepted scope, preserving canonical identities and live linkages where supported.
5. VERIFY fresh canonical read-back through [layout-evidence](../protocol/layout-evidence.md). Update project decision/revision records only for actual approved/applied changes, then resume authorized dependent screens.
6. For migrations, compare affected screens and states with the before-state: content, interaction, responsive behavior, linkage and geometry. PRESENT canonical results separately from screen acceptance.

**Complete when:** approved definitions and authorized migrations are applied and verified, or unresolved failures are explicitly incomplete. Unaffected consumers remain unchanged.

**Recovery:** inspect partial writes, halt dependent operations, and use the approved rollback strategy where safe. Inability to verify a critical canonical operation blocks dependent work; a failed verification never expands authorization.
