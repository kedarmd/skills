# New product

**Use when:** discovery confirms there is no existing product baseline. Defining behavior: establish approved foundations before dependent screens.

**Inputs:** product goals, users, workflows, platform, realistic content, accessibility needs, viewports, and available tools.

1. Run DISCOVER; if UI or a system already exists, use [audit](audit.md) to reconcile it instead of replacing it.
2. Establish candidate foundations, components, states, compositions, and responsive rules through [system-model](../protocol/system-model.md). Research direction through [inspiration](inspiration.md) only when useful.
3. Use [design-system change](design-system-change.md) to present a scoped noncanonical proposal. Explore feasibility in isolation; approval blocks canonical creation and dependent screens, not independent research.
4. After approval, apply and verify canonical definitions, then use [new-screen](new-screen.md) within the approved contract.

**Complete when:** the approved baseline has identifiable authority, applied canonical assets are verified, and any requested screens have separate verification and acceptance status.

**Recovery:** unresolved requirements or rejected proposals return to CONTRACT; preserve isolated drafts as proposals. Missing tools limit evidence rather than justify invented canonical assets or a success claim.
